# Ticket 98 — AI One-Line Run Summaries

## Goal

Each submitted run's accordion header shows a **meaningful one-line status
report** of what actually happened — generated by the task's AI provider
(falling back to the default AI service, §1) reflecting on the task itself
plus the run's inputs and output. The header
becomes the user's quick-read on the run; for multi-run cards, the
collapsed group header carries the latest run's summary.

## Current behavior (the bug)

`summarize()` in
[SubmissionAccordionRow.tsx](../src/mainview/components/SubmissionAccordionRow.tsx)
echoes the first non-empty input value. In the beginner profile's failed
"Create Media Post" run that surfaces the AI-prompt field text ("Describe
your post…") — the header parrots the _question_ instead of describing the
_result_. Same string feeds the collapsed group header via
[FormCardHeader.tsx](../src/mainview/components/FormCardHeader.tsx)'s
`summary` prop.

## Acceptance criteria

### 1. Generation (Bun side)

- New `src/bun/ai/runSummary.ts`: after a run reaches `success` or `error`,
  compose a **self-reflection prompt** from the task's own definition —
  name, description, field labels + submitted values, the compiled command,
  exit status, and captured stdout/stderr (tail-truncated to a sane token
  budget) — and ask for **one elegant line** (≤ ~90 chars, no leading
  status word — the status icon already says failed/succeeded; the line
  says _what_ and _why_). E.g. `Publish to Youtube + X failed: network
unreachable` or `Backed up ~/Documents → 42 MB zip`.
- Provider selection mirrors [magicFill.ts](../src/bun/ai/magicFill.ts):
  the task's `aiProvider` if credentialed, else the default AI service.
  **No AI configured → skip silently** and keep the fallback (§3).
- Fire-and-forget after run completion in
  [execute.ts](../src/bun/runner/execute.ts) — never blocks or fails the
  run; AI errors degrade to the fallback.
- Persist to `history.db` as additive `summary TEXT NULL`
  ([migrations.ts](../src/bun/db/migrations.ts)); `RunRecord.summary?`
  pushed to the renderer via the existing run-update stream so headers fill
  in when generation lands.

### 2. Display

- Accordion row header shows `run.summary` when present; a subtle shimmer/
  placeholder while a just-finished run's summary is pending.
- Collapsed multi-run group header shows the **latest** run's summary; if
  the group has mixed outcomes, prefix with a terse rollup (e.g. `3 runs,
1 failed — <latest summary>`). Keep it one truncating line.
- Scheduled runs keep the current formatted-date header (nothing has
  happened yet — no AI call).

### 3. Fallback heuristic

- When no summary exists (no AI, generation failed, legacy runs), improve
  the current heuristic: `error` → first stderr line if available else
  "Failed"; `success` → `<field label>: <value>` of the first filled field
  (label included so it stops reading as a bare question).

## Edge cases

- Huge outputs: truncate input to the model, never the stored raw output.
- Secrets: submitted values may be sensitive — **no masking primitive
  exists yet** (ticket 71 built none; verified). This ticket owns the
  minimal version: an optional `secret?: boolean` on the field definition
  (settable in the wizard field editor, default off) and one shared
  `maskSecrets(values, fields)` helper that replaces secret values with
  `•••` before they reach any AI prompt. Tickets 99 and 106 reuse this
  flag/helper — don't gold-plate it here.
- Ollama/local models can be slow — summaries are eventually-consistent by
  design; the UI must look fine forever-pending.
- Workflow step runs: summarize the workflow run once at the run level
  (trace already explains steps); don't fan out one AI call per step.
  Workflow runs are JSON records in
  [runStore.ts](../src/bun/workflows/runStore.ts), **not** `history.db` —
  persist theirs as `WorkflowRun.summary?`, written by
  [engine.ts](../src/bun/workflows/engine.ts) on completion; the run-log
  header (ticket 94) displays it.
